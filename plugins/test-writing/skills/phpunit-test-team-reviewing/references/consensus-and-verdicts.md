# Consensus & Verdicts — Adaptation Guide

Computed deterministically from the binding stances — Wave-1 peer stances in the review stage, updated by the Wave-3 defense fold and arbitration when the adversarial stage runs. The script (`mergeUnit` / `mergeFile` / `bucketFile` + arbitration) owns the computation; this is the consensus policy and its adaptation surface.

## Consensus policy

- **Finding identity** — `finding_id` = `${rule_id}|${methodId(method) || 'class-level'}|${fingerprint}`, where `methodId` strips a trailing `(...)` call suffix and surrounding whitespace from `method` (so `testFoo()` and `testFoo` are the same locator), `'class-level'` stands in where `method` is absent or empty, and the fingerprint is a stable hash of the whitespace-normalized `current` (of the `summary` where `current` is empty). Line numbers take no part in it: one defect two reviewers placed at `:43` and `:47` is one finding, and two different defects under one rule in one method stay two, neither borrowing the other's votes. Reviewing agents never emit a `finding_id` — the workflow stamps every finding as it arrives, and every later role quotes back the id it was handed.
- **Per unit, per `finding_id`** — 3-of-3 unanimous → include (no dissent); 2-of-3 majority → include with a dissent annotation from the reviewer who omitted it; 1-of-3 minority → exclude from the body, record as contested.
- **Cross-track merge** — merge within each unit's 3 stances, then union per file by `finding_id`; a finding that reaches consensus in any unit wins over a contested one, and the two units' remediation and location lists are unioned rather than the loser's being dropped. The union runs unit by unit in one pass, so a finding that alternates between the kept and contested sides across units still lists its locations in the order the units met them, not grouped by which side each came from.
- **Enforce-level conflict** — take the majority enforce level, note the disagreement.
- **Remediation payload** — every distinct remediation the stances proposed survives. Duplicates collapse under whitespace normalization; the rest are ordered longest first in `suggested_variants`, and `suggested` is the first — the most complete one. `location`, `summary`, `current`, and `method` come from the record that supplied it, so `current` and `suggested` describe one change, and `locations` carries every location the stances reported, first seen first. Where that record carries no value of its own for one of those four fields — possible only for a payload whose schema does not require it, such as a defender's `re_adopted`/`adopted_new` entry — the field falls back to the record it was merged with rather than being dropped. *No value* means the field is absent, never that it is empty: a `current` of `""` is a finding that quoted no code (the state the identity fingerprint falls back to `summary` for) and a `method` of `""` is the `class-level` locator `methodId` reads it as, so each stands as that record's own value and neither borrows another record's. `title` is the one field that never takes the paired record's value directly: it is the owner's own `title` when it has one, else a short form of whichever `summary` won the fallback above — so the title always describes the summary actually rendered, never the paired record's title. Unlike the other four fields, an owner's blank `title` (`""`) also counts as absent here and falls through to the summary-derived form. No stance's remediation is discarded at any stage.
- **Status** — `ISSUES_FOUND` (1+ must-fix in any file); else `NEEDS_ATTENTION` (warnings, consistency findings, or "split this class" / informational); else `PASS`.

## What you can adapt

- The **vote thresholds** (3-of-3 / 2-of-3 / 1-of-3).
- The **variant ordering** in `suggested_variants` (longest first) and which fingerprint the identity hashes — never whether the non-leading variants are kept: dropping one loses a remediation nothing downstream can recover.
- **Arbitration** (adversarial stage) — contested findings are arbitrated up to the preset's **hard caps**: `arbFile` per file, then `arbMax` per run, candidates sorted must-fix-first at both levels so the caps trim the lowest-severity tail first; every trimmed finding stays contested and visible. An arbitrated contested **must-fix** gets **3 adversary-tier arbiters** (opus on the default model combo) and a majority verdict: ≥ 2 `confirmed` → include (+ `corrected_enforce`); ≥ 2 `refuted` → exclude/contested; no majority → **keep**, marked `arbitration: split` (a possibly-real must-fix is never silently dropped). should-fix / consider keep a **single** body-tier arbiter: `confirmed` → include; `refuted` → exclude/contested; `uncertain` → keep contested.

## Already handled — do not re-adapt

- **Adversary-impact tagging** — every finding carries `unchanged` / `defended` / `overturned` / `resurrected` / `introduced` (all `unchanged` when the adversarial stage was skipped at the gate).
- **Cross-file findings** — the dedicated cross-file agent (the `signals` stage) is their sole producer (fingerprint input → `consistency[]` warnings; counts toward `NEEDS_ATTENTION`, never `ISSUES_FOUND`).
- **"Split this test class"** — an `L > C` file emits a first-class informational entry; its method-shard and digest findings still merge.
- **Coverage overlaps & placement flags** — the cross-cutting SUT-coverage map (`coverage_overlap[]`) and the integration-to-unit placement flags (`placement_flags[]`) are computed deterministically by the skill's merge step from the manifest + the merged INTEGRATION-008 consensus signal. They are **informational**: they never raise status to `ISSUES_FOUND`, form their own finding class separate from quality findings, and only point at the standalone `phpunit-integration-to-unit-migrating` skill.
- **Per-finding `method` / `branch_touched` / `implies_src_change`** — every finding carries the method it occurs in (the stable locator; `class-level` for structural), a `branch_touched` flag computed post-merge from the manifest's `changed_methods` on diff-scoped runs (`null` otherwise), and `implies_src_change` (true when **any** clustered stance flagged it — the fix needs a production change). All three are informational metadata: none change consensus or status. Rendered shape in report-format.md.
- **Defense-stage promotion identity** — an adoption or re-adoption resolves its `finding_id` against the record that already carries it, searched in one file's scope only: the consensus entry (kept or contested), then the withdrawn original the review stage persisted beside the withdrawal in `adversarial_input.withdrawn_originals` (a finding every peer withdrew survives in neither set, so a resurrection of it would otherwise resolve to nothing; the stored original is the finding's most-merged state at the withdrawal — the Wave-0 stances that reported it unioned with the reconciler stances that maintained it afterwards, so a remediation a peer pass first proposed and a later pass withdrew is restored with it; where two units of one file both withdrew the id, both units' contributors merge into one stored original rather than the first unit's standing alone), then the red team's own `new_findings` entry. An id resolving to none of them is a broken back-reference and stops the run. `finding_id` and `rule_id` are that record's and only that record's, so a defender cannot re-label the finding it names. The remaining fields follow the remediation as everywhere else: `method`, `location`, `summary`, and `current` come from whichever record supplied `suggested_variants[0]` — the resolved original, or the defender whose remediation leads — falling back to the original for any field that record does not carry at all, so a defender omitting `method` still cannot downgrade a method-level finding to `class-level`. `title` is the one field that never takes the paired record's value directly: it is the owner's own `title` when it has one, else a short form of whichever `summary` won the fallback above — so the title always describes the summary actually rendered, never the paired record's title. `enforce` is the defenders' majority over the voting entries: a defender that lists one finding twice is one voice in that tally, and the repeat entry's remediation and location still merge in — at the point the entry was seen, not behind the last defender's, so `locations` stays first-seen across defenders. The promoted record then reconciles against `kept`/`contested` by that same id — merged into whichever set already carries it, spliced out of `contested` when the merge lands in `kept` — instead of being appended as a fresh duplicate.
- **Adversary new findings are indexed per file** — `finding_id` embeds no path, so the red team's `new_findings` are keyed by the file they were raised against; one id on two files names two defects and never cross-resolves. Two lens adversaries raising the same id on one file are one finding, their remediations unioned rather than the later one overwriting the earlier.
